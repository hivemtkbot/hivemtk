# 对话驱动自我学习与自我矫正机制

> 适用范围：hivemtk 用户端（开源客服系统）
> 设计依据：复用现有 `feedback_loop` / `confidence` / `event` / `async` 基础设施，补齐"对话开始即触发"的实时自我学习闭环
> 五层架构归属：L3 业务层（编排） + L4 能力层（自我学习引擎）
> 文档版本：v1.0

---

## 一、背景与目标

### 1.1 现状

项目已具备完善的"事后反馈学习"基础设施：

| 模块 | 位置 | 能力 | 触发时机 |
| --- | --- | --- | --- |
| FeedbackCollector | `service/feedback_loop/feedback_collector.go` | 异步队列采集 10 类反馈信号，奖励计算 + 落库 | 主链路 Collect 调用 |
| ChampionDialogueAnalyzer | `service/feedback_loop/champion_dialogue_analyzer.go` | 销冠对话 pgvector 聚类 + LLM 话术提取 | 每周日 03:00 |
| PromptIterator | `service/feedback_loop/prompt_iterator.go` | 基于负反馈生成 Prompt 候选 | 每日 04:00 |
| SOPAutoOptimizer | `service/feedback_loop/sop_auto_optimizer.go` | SOP 自动应用 + A/B + 回滚 | 日级 |
| BanditAllocator | `service/feedback_loop/bandit_allocator.go` | Thompson Sampling 流量分配 | 每 6 小时 |
| Confidence 模块 | `service/confidence/*.go` | 9 维置信度聚合 + 动态阈值 + 转人工 | 对话中实时 |
| EventBus | `internal/event/bus.go` | 进程内事件总线，双队列（critical/normal）+ 优雅关闭 | 启动期订阅 |
| async 工具 | `pkg/utils/async/background.go` | `RunWithTimeout` / `RunDetach` / `SafeGo`（含 panic 恢复） | 任意 |
| AssetBundle | `model/asset_bundle.go` | OpenAI ChatML 协议资产包，scope/status/version | 人工编辑 |
| RAG 引擎 | `aiagent/rag/*` | pgvector + BM25 混合检索，metrics + safety_guard | 被动检索 |

### 1.2 核心缺口（用户需求要解决）

1. **触发时机错位**：现有 feedback_loop 是"日/周/月定时"，不是"对话开始即触发"。用户要求"一旦进入对话开始，利用 Go 协程特性"实现自我学习。
2. **RAG 缺乏自我矫正**：
   - 召回结果没有基于对话反馈回流到知识库
   - 低质语料没有被自动标记/降权/淘汰
   - 销冠话术没有被自动向量化补录到 RAG 知识库
3. **资产包缺乏自我学习**：
   - AssetBundle 是静态的（人工创建/编辑），UseCount/Rating 字段存在但未驱动自动迭代
   - 没有基于对话效果（reward）自动生成资产包候选
   - 没有"销冠对话 → 自动生成资产包"的回流管道
4. **协程编排不足**：
   - 现有 goroutine 多为单点 `go func`，缺少"对话开始 → 多协程并行自我学习"的编排
   - EventBus 已有但未被自我学习场景订阅

### 1.3 设计目标

| 目标 | 衡量指标 |
| --- | --- |
| 对话开始即触发自我学习 | WS 连接建立后 100ms 内发布 `dialogue.started` 事件，订阅协程异步消费 |
| RAG 自我矫正 | 低质语料 24h 内被打标降权；销冠话术 1h 内回流到向量库；召回质量 P95 提升 |
| 资产包自我学习 | 高 reward 对话 7 天内生成资产包候选；A/B 测试后自动上线；低效资产包自动降级 |
| 协程安全 | 所有自我学习协程经 `async.SafeGo` 包装；panic 不影响主链路；支持优雅关闭 |
| 不阻塞主链路 | 自我学习全部异步，主链路附加延迟 < 5ms |
| 复用现有基础设施 | 100% 复用 EventBus / FeedbackCollector / ChampionAnalyzer / async 工具 |

## 二、需求规格

### 2.1 功能需求

#### FR-1 对话开始事件发布
- **FR-1.1** WebSocket 连接建立且首条访客消息到达时，`chat_visitor_service.go` 必须通过 `event.Publish(TopicDialogueStarted, payload)` 发布"对话开始"事件
- **FR-1.2** payload 包含：`session_id` / `visitor_id` / `customer_id`（可选）/ `scenario` / `first_message` / `trace_id` / `started_at`
- **FR-1.3** 事件必须经 critical 队列投递（避免被旁路事件洪峰挤掉）
- **FR-1.4** 发布失败必须降级为日志告警，不得阻塞主链路

#### FR-2 对话结束事件发布
- **FR-2.1** 会话进入 `closed` 状态时，`customer_session.go` 必须发布 `dialogue.ended` 事件
- **FR-2.2** payload 包含：`session_id` / `duration_sec` / `outcome`（converted/abandoned/transferred）/ `aggregated_reward` / `signal_breakdown` / `trace_id`

#### FR-3 RAG 自我矫正（对话开始触发）
- **FR-3.1** 订阅 `dialogue.started` 事件，启动协程执行 RAG 预热：基于 `first_message` 预查询 RAG，将 Top-K 召回结果缓存到 Redis（TTL 5min），供后续 LLM 调用复用
- **FR-3.2** 订阅 `dialogue.ended` 事件，启动协程执行 RAG 反思：
  - 若 `aggregated_reward < -0.5`（负反馈）：标记本次召回的 Top-K 语料为"低质嫌疑"，累计 3 次降权 50%，累计 10 次归档
  - 若 `aggregated_reward >= 1.5`（高 reward）：将本次对话的 `customer_msg + ai_reply` 向量化后写入 `knowledge_corpus` 表（source=`dialogue_extract`），打标 `quality=champion`
- **FR-3.3** RAG 反思必须幂等：相同 `session_id` 仅处理一次（基于 `self_learning_logs` 表的去重）
- **FR-3.4** RAG 反思失败必须落库 `self_learning_logs.status=failed` + `error_msg`，供重试

#### FR-4 资产包自我学习（对话结束触发）
- **FR-4.1** 订阅 `dialogue.ended` 事件，当 `aggregated_reward >= 2.0` 且 `outcome=converted` 时，启动协程：
  - 调用 `ChampionDialogueAnalyzer.AnalyzePipeline` 提取话术
  - 将话术打包为 AssetBundle 候选（status=draft, scope=private, source=`self_learning`）
  - 写入 `asset_bundle_candidates` 表，关联 `session_id` 与 `extracted_scripts`
- **FR-4.2** 当某候选累计被生成 ≥ 3 次（聚类相似度 ≥ 0.85），自动升级为 A/B 测试候选：
  - 在 `asset_bundle_ab_tests` 表登记实验
  - 通过 `BanditAllocator` 分配流量（现役资产包 vs 候选）
  - A/B 周期 7 天，收敛后自动 PromoteArm
- **FR-4.3** 当某 active 资产包连续 30 天 `use_count=0` 或 `rating < 2.0` 且样本数 ≥ 50，自动降级为 inactive，并发布 `asset.degraded` 事件

#### FR-5 自我学习看板
- **FR-5.1** 提供 `GET /api/v1/self-learning/overview` 接口，返回：
  - 今日触发次数 / 成功 / 失败 / 降级
  - RAG 语料增删统计（champion 补录数 / 低质归档数）
  - 资产包候选数 / A/B 实验数 / 自动上线数 / 自动降级数
- **FR-5.2** 提供 `GET /api/v1/self-learning/logs` 接口，支持按 `scenario` / `status` / `time_range` 筛选

### 2.2 非功能需求

| 维度 | 指标 |
| --- | --- |
| 性能 | 主链路附加延迟 < 5ms；自我学习协程 P95 完成时延 < 30s |
| 可靠性 | 事件投递成功率 ≥ 99.9%（队列满降级日志）；幂等保证 100% |
| 可观测 | 每次自我学习落库 `self_learning_logs`；Prometheus 指标暴露 |
| 资源 | 单实例自我学习协程并发上限 16（信号量）；超限丢弃并告警 |
| 优雅关闭 | 主进程收到 SIGTERM 后，自我学习协程 30s 内排空当前任务退出 |
| 安全 | 资产包候选必须人工审核或 A/B 收敛后才上线；不得直接覆盖 active 资产包 |
| 架构合规 | 100% 遵守 Go 五层架构；禁止 controller 直访 repository；禁止 import cycle |

### 3.3 协程模型设计

#### 3.3.1 触发协程（事件订阅者）

```go
// self_learning_orchestrator.go 核心结构
type SelfLearningOrchestrator struct {
    bus             *event.EventBus
    ragCorrector    *RAGSelfCorrector
    assetLearner    *AssetBundleLearner
    semaphore       chan struct{}          // 容量 16，控制并发
    db              *gorm.DB
    logRepo         repository.SelfLearningLogRepository
    stopCh          chan struct{}
    wg              sync.WaitGroup
}

// Start 在 main.go 启动阶段调用，订阅事件
func (o *SelfLearningOrchestrator) Start() {
    o.bus.Subscribe(event.TopicDialogueStarted, o.onDialogueStarted)
    o.bus.Subscribe(event.TopicDialogueEnded, o.onDialogueEnded)
    o.bus.Subscribe(event.TopicAssetDegraded, o.onAssetDegraded)
}

// onDialogueStarted 处理对话开始事件
func (o *SelfLearningOrchestrator) onDialogueStarted(evt event.Event) error {
    payload, _ := evt.Payload.(DialogueStartedPayload)
    // 幂等检查：相同 (session_id, scenario) 仅处理一次
    if o.logRepo.Exists(evt.Topic, payload.SessionID) {
        return nil
    }
    // 信号量控制并发
    select {
    case o.semaphore <- struct{}{}:
        o.wg.Add(1)
        async.SafeGo(func() {
            defer o.wg.Done()
            defer func() { <-o.semaphore }()
            ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
            defer cancel()
            o.ragCorrector.Warmup(ctx, payload)  // FR-3.1
        })
        return nil
    default:
        // 信号量满，丢弃并告警
        logger.Warnf("[self-learning] semaphore full, drop warmup session=%s", payload.SessionID)
        return nil
    }
}
```

#### 3.3.2 协程生命周期

| 阶段 | 行为 |
| --- | --- |
| 启动 | `main.go` 调用 `orchestrator.Start()`，订阅事件（必须在 EventBus 启动后） |
| 运行 | 每个事件触发一个 `SafeGo` 协程，独立 panic 恢复，独立超时 |
| 关闭 | `main.go` 收到 SIGTERM → `orchestrator.Stop()` → `close(stopCh)` → `wg.Wait()` 排空（最长 30s） |

#### 3.3.3 并发与去重

- **并发上限**：信号量 `chan struct{}` 容量 16（可配置 `self_learning.max_concurrency`）
- **幂等保证**：`self_learning_logs` 表 `UNIQUE(session_id, scenario)`，触发前先查存在性
- **超时控制**：每个协程 `context.WithTimeout(30s)`，防止卡死
- **panic 恢复**：`async.SafeGo` 已封装 defer recover

### 3.4 RAG 自我矫正策略

#### 3.4.1 预热阶段（dialogue.started 触发）

```go
// rag_self_corrector.go
func (r *RAGSelfCorrector) Warmup(ctx context.Context, p DialogueStartedPayload) error {
    // 1. 调用 RAG 引擎预查询（复用 rag_service.go）
    topK, err := r.ragService.Retrieve(ctx, p.FirstMessage, 5)
    if err != nil {
        return r.logRepo.MarkFailed(ctx, p.SessionID, "rag_warmup", err)
    }
    // 2. 缓存到 Redis（key: rag:warmup:{session_id}, TTL 5min）
    cacheKey := fmt.Sprintf("rag:warmup:%s", p.SessionID)
    return r.redis.Set(ctx, cacheKey, topK.JSON(), 5*time.Minute).Err()
}

// 后续 LLM 调用时优先读缓存（rag_engine.go 增加 cacheLookup）
```

#### 3.4.2 反思阶段（dialogue.ended 触发）

```go
func (r *RAGSelfCorrector) Reflect(ctx context.Context, p DialogueEndedPayload) error {
    if p.AggregatedReward < -0.5 {
        return r.markLowQualityCorpus(ctx, p)
    }
    if p.AggregatedReward >= 1.5 {
        return r.upsertChampionCorpus(ctx, p)
    }
    return nil  // 中性反馈不处理
}

// markLowQualityCorpus 标记低质语料
func (r *RAGSelfCorrector) markLowQualityCorpus(ctx context.Context, p DialogueEndedPayload) error {
    // 1. 查本次 session 用过的 Top-K 语料（从 rag:used:{session_id} 读）
    usedIDs := r.redis.SMembers(ctx, fmt.Sprintf("rag:used:%s", p.SessionID)).Val()
    // 2. 累加 low_quality_hits；累计 3 次降权 50%，累计 10 次归档
    return r.corpusRepo.BatchUpdateQuality(ctx, usedIDs, -1, map[int]int{3: 50, 10: 100})
}

// upsertChampionCorpus 销冠对话补录
func (r *RAGSelfCorrector) upsertChampionCorpus(ctx context.Context, p DialogueEndedPayload) error {
    // 1. 取 session 最近一条 customer_msg + ai_reply
    msg, reply := r.fetchLastExchange(ctx, p.SessionID)
    // 2. 向量化（复用 embedding_service.go）
    vec := r.embedder.Embed(msg + " || " + reply)
    // 3. 写入 knowledge_corpus（source=dialogue_extract, quality=champion）
    return r.corpusRepo.UpsertChampion(ctx, msg+" || "+reply, vec, p.SessionID)
}
```

#### 3.5.2 聚类升级（每日定时检查）

```go
// ClusterUpgradeCron 每日 05:00 执行
func (l *AssetBundleLearner) ClusterUpgradeCron(ctx context.Context) {
    // 1. 拉取所有 status=candidate 且未进入 A/B 的候选
    candidates := l.candidateRepo.ListPending(ctx)
    // 2. pgvector 聚类（复用 ChampionAnalyzer 的聚类逻辑）
    clusters := l.clusterCandidates(candidates)
    // 3. 簇大小 >= 3 → 创建 A/B 实验
    for _, cluster := range clusters {
        if len(cluster) < 3 { continue }
        l.createABTest(ctx, cluster)
    }
}

func (l *AssetBundleLearner) createABTest(ctx context.Context, cluster []AssetBundleCandidate) error {
    // 1. 合并 cluster 中的 messages 为单一候选资产包
    merged := l.mergeMessages(cluster)
    // 2. 找到该 scenario 下的现役资产包作为 baseline
    baseline := l.assetRepo.FindActiveByScenario(ctx, cluster[0].Scenario)
    // 3. 创建实验
    exp := &model.AssetBundleABTest{
        ExperimentID:     genExperimentID(),
        BaselineAssetID:  baseline.AssetID,
        CandidateID:      merged.CandidateID,
        Scenario:         cluster[0].Scenario,
        TrafficSplit:     `{"baseline":0.5,"candidate":0.5}`,
        Status:           "running",
    }
    return l.abTestRepo.Create(ctx, exp)
}
```

#### 3.5.3 流量分配与收敛

- 复用 `BanditAllocator`（Thompson Sampling），按 `aggregated_reward` 反馈自动分配流量
- 每 6 小时检查收敛：`ConvergenceThreshold=0.95` → `PromoteArm` → 候选升级为 active，原 baseline 降级为 inactive
- A/B 周期 7 天，未收敛则延长至 14 天，仍不收敛则 rollback

## 四、头脑风暴二次论证

### 4.1 多视角评估

#### 视角 1：性能（主链路影响）
- ✅ 优势：事件发布是 channel 入队，<1ms；自我学习全异步，主链路附加延迟 < 5ms
- ⚠️ 风险：高并发对话（QPS > 1000）时 EventBus critical 队列可能积压
- 对策：critical 队列容量提升到 4096；信号量限制自我学习并发到 16；超出丢弃并告警（best-effort 设计）

#### 视角 2：可靠性（数据一致）
- ✅ 优势：`self_learning_logs` UNIQUE(session_id, scenario) 保证幂等；事务化落库
- ⚠️ 风险：RAG 反思失败但 feedback_signals 已聚合，会导致语料标记遗漏
- 对策：失败任务落库 status=failed，每小时重试 cron 扫描重试 3 次

#### 视角 3：安全（防止错误学习）
- ✅ 优势：资产包候选 status=draft，必须 A/B 收敛后才上线；不直接覆盖 active
- ⚠️ 风险：销冠话术补录到 RAG 可能引入"刷单对话"污染
- 对策：
  - 销冠补录需 `is_champion=true` 标记 + `aggregated_reward >= 1.5` 双重门槛
  - 单 session 最多补录 1 条语料，防止单一对话刷量
  - 看板提供"语料回滚"接口，可一键撤销某 session 的补录

#### 视角 4：可观测性
- ✅ 优势：每次自我学习落库 `self_learning_logs`，全链路 trace_id 串联
- ⚠️ 风险：自我学习协程 panic 后无 trace
- 对策：`async.SafeGo` 已有 recover，panic 时落库 `status=failed` + `error_msg=panic: xxx`

#### 视角 5：架构合规
- ✅ 优势：100% 遵守五层架构，所有依赖通过构造函数注入
- ⚠️ 风险：`SelfLearningOrchestrator` 在 service 层订阅 event，可能引入 service → event → service 循环
- 对策：event 包是基础设施（无业务依赖），不构成循环；orchestrator 仅依赖 event 的 Publish/Subscribe API

#### 视角 6：与现有 feedback_loop 的关系
- ✅ 优势：完全互补——feedback_loop 负责"日/周/月级"深度学习，本机制负责"对话级"实时学习
- ⚠️ 风险：职责重叠（如 ChampionAnalyzer 被两边调用）
- 对策：本机制只调用 ChampionAnalyzer 的 `AnalyzePipeline` 方法，不修改其内部；feedback_loop cron 仍然保留月度/周度任务

#### 视角 7：资源消耗
- ✅ 优势：协程复用，单实例并发上限 16
- ⚠️ 风险：pgvector 聚类 O(n²) 在候选多时可能慢
- 对策：聚类限制 `MaxDialoguesPerRun=500`（已有配置）；超限分批处理

#### 视角 8：冷启动
- ✅ 优势：对话开始即触发，无需预热数据
- ⚠️ 风险：新部署系统无 feedback_signals 数据，反思阶段无 reward 可用
- 对策：反思阶段遇 `aggregated_reward=0` 时跳过（中性），不触发任何动作；待 7 天数据积累后自然启动

### 4.2 风险识别与对策

| 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- |
| EventBus 队列积压 | 中 | 中 | critical 队列扩容到 4096；超出丢弃并告警 |
| 自我学习协程 panic | 低 | 低 | SafeGo 已封装 recover；落库 failed 状态 |
| 销冠话术被刷单污染 | 中 | 高 | 双重门槛 + 单 session 限 1 条 + 看板回滚接口 |
| 资产包候选爆炸 | 低 | 中 | 候选表 7 天清理一次（status=rejected 自动归档） |
| A/B 实验不收敛 | 中 | 中 | 7 天 → 14 天 → rollback； BanditAllocator 已有收敛检查 |
| RAG 低质误判 | 中 | 中 | 降权 50% 而非直接归档；累计 10 次才归档；看板可手动恢复 |
| 数据库锁竞争 | 低 | 中 | 反思阶段用 `UPDATE WHERE` 而非事务锁；批量操作错峰执行 |
| 主进程关闭时任务丢失 | 中 | 低 | Stop() 排空 30s；未完成任务落库 status=pending 供重启重试 |

### 4.3 方案选型对比

#### 选型 1：触发机制 — EventBus vs 直接 go func
| 方案 | 优势 | 劣势 | 选择 |
| --- | --- | --- | --- |
| EventBus | 解耦、可观测、已实现 | 队列满可能丢弃 | ✅ 选 |
| 直接 go func | 简单 | 无法限流、无去重、无观察 | ❌ 弃 |

#### 选型 2：协程调度 — 信号量 vs worker pool
| 方案 | 优势 | 劣势 | 选择 |
| --- | --- | --- | --- |
| 信号量 | 简单、足够 | 无优先级 | ✅ 选（16 并发足够） |
| worker pool | 可优先级 | 复杂、过度设计 | ❌ 弃 |

#### 选型 3：候选上线 — 自动 promote vs 人工审核
| 方案 | 优势 | 劣势 | 选择 |
| --- | --- | --- | --- |
| A/B 收敛后自动 promote | 全自动闭环 | 收敛判定错误风险 | ✅ 选（BanditAllocator 已有收敛阈值 0.95） |
| 人工审核 | 安全 | 失去"自我学习"意义 | ❌ 弃（但保留看板手动 reject 接口） |

#### 选型 4：RAG 反思粒度 — session 级 vs message 级
| 方案 | 优势 | 劣势 | 选择 |
| --- | --- | --- | --- |
| session 级 | 简单、与 feedback_signals 一致 | 粒度粗 | ✅ 选 |
| message 级 | 精细 | 需额外信号源、复杂 | ❌ 弃（未来 P2 演进） |

## 七、扩展设计：三位一体机制 + 全自动开关 + 同行参考

> 本章节是对前六章的扩展，响应用户需求："不管是知识库还是资源包，都要支持自动的 自我监督 自我学习 自我矫正，这是一套机制，用户开启就要全自动执行"。
> 文档版本：v1.1

### 7.1 业界同行设计参考

基于 2025 年业界主流实现调研，提炼 6 类核心设计模式作为本机制的理论依据：

#### 7.1.1 Self-RAG / CRAG / SH-RAG（自我矫正 RAG 三剑客）

| 框架 | 核心机制 | 借鉴点 |
| --- | --- | --- |
| **Self-RAG**（IBM/论文） | 模型用特殊 control token 自我决定何时检索、评估检索结果、批评自身输出 | 自我批评 token 化 → 我们的 quality_label 字段 |
| **CRAG**（Corrective RAG） | Retrieval Evaluator 对召回打 3 标签：Correct/Incorrect/Ambiguous → 触发 refine/web_search/both | 三态评估 → 我们的 reward 三段阈值（<-0.5 / [-0.5,1.5) / >=1.5） |
| **SH-RAG**（Self-Healing RAG, IET 2025） | 3 组件：Self-Verification + Retrieval Refinement + Self-Feedback Learning Loop | 三组件架构 → 我们的三位一体（监督/矫正/学习） |
| **SCMRAG**（AAMAS 2025） | LLM agent 自主识别缺失信息，从外部 web 补充 | 外部知识补充 → 资产包候选从 platform-server 拉取 |

#### 7.1.2 LangGraph Reflection / Reflexion（自我反思）

- **Reflection 模式**：生成者 + 批评者双身份迭代，直到达到质量阈值（QUALITY_THRESHOLD=0.8, MAX_ITERATIONS=3）
- **Reflexion 模式**：将反思转化为可重用知识（外部记忆）
- **借鉴**：自我批评循环 + 反思知识化 → 我们的 `self_learning_logs` + `knowledge_corpus` 双写

#### 7.1.3 DSPy（自动 Prompt 优化）

- **核心理念**：Program, don't prompt（编程而非写提示词）
- **3 抽象**：Signatures（做什么）/ Modules（怎么做）/ Optimizers（自动优化）
- **BootstrapFewShot**：强模型教弱模型，自动生成 few-shot 示例
- **借鉴**：自动 prompt 优化 → 我们复用现有 `PromptIterator` + `BanditAllocator` 已实现此能力

#### 7.1.4 Closed-Loop RAG（Fractal.ai 2025 闭环设计）

**三阶段范式**（最核心借鉴）：
1. **Phase 1: Rigorous Instrumentation** — 双维度监控（Retriever + Generator）
2. **Phase 2: Diagnosis** — 失败矩阵定位根因
3. **Phase 3: Agentic Intervention** — 派遣 agent 自动修复

**失败矩阵**（直接采纳）：

| Retriever Score | Generator Score | 诊断 | 修复策略 |
| --- | --- | --- | --- |
| Low | N/A | 召回失败 | Query 重写（HyDE）/ Query 拆解 / 元数据过滤 |
| High | Low (Faithfulness) | LLM 幻觉 | 降温 / 强制引用 / 重新生成 |
| High | Low (Relevance) | LLM 跑题 | Prompt 重写 / 重新路由 |

**指标体系**（采纳）：
- Retriever：Context Precision / Context Recall / Hit Rate（用 LLM-as-Judge 估算）
- Generator：Faithfulness（groundedness）/ Answer Relevance

#### 7.1.5 Self-Improving Agentic RAG（5 层架构）

```
1. Entry Router          → 路由
2. Core Agentic Pipeline → 核心管道
3. Evaluation Layer      → 评估层（TruLens/RAGAS/ARES）
4. Improvement Agents    → 改进 agent（prompt/retriever/routing/data）
5. Feedback Store        → 反馈存储 + 调度
```

**借鉴**：5 层架构 → 我们的自我监督 5 维度（见 7.2）

#### 7.1.6 Iterative Feedback-Driven RAG（双循环）

- **Operational Loop**：query → retrieve → generate → respond
- **Feedback Loop**：collect → adjust_relevance_scores → fine_tune_index
- **借鉴**：双循环 → 我们的主链路（同步）+ 自我学习（异步）双循环

### 7.2 三位一体机制设计

基于上述同行设计，将原"自我学习"扩展为**三位一体闭环**：

```
┌─────────────────────────────────────────────────────────────┐
```

#### 7.2.1 自我监督（Self-Supervision）— 新增维度

**5 维监控指标**（参考 Closed-Loop RAG + RAGAS）：

| 维度 | 指标 | 计算方式 | 阈值 |
| --- | --- | --- | --- |
| 召回精度 | Context Precision | LLM-as-Judge 对 Top-K 打 relevance 分 | < 0.6 触发矫正 |
| 召回覆盖 | Context Recall | 命中关键词覆盖率 | < 0.5 触发矫正 |
| 生成忠实度 | Faithfulness | 答案是否被召回内容支撑（LLM-as-Judge） | < 0.7 触发矫正 |
| 答案相关性 | Answer Relevance | 答案是否回应 query（LLM-as-Judge） | < 0.7 触发矫正 |
| 资产包效能 | Asset Effectiveness | reward / use_count 比值 | < 0.3 触发降级 |

**监控触点**：
- 对话中：实时采集 5 维信号（异步、不阻塞主链路）
- 对话结束：聚合 session 级 5 维分数，落库 `self_supervision_signals`
- 定时（每小时）：聚类失败模式，触发 targeted improvement

#### 7.2.2 自我矫正（Self-Correction）— 失败矩阵驱动

**失败矩阵 + 修复策略**（采纳 Closed-Loop RAG 设计）：

| 失败场景 | 触发条件 | 修复动作 | 责任模块 |
| --- | --- | --- | --- |
| 召回失败 | Context Precision < 0.6 | HyDE 重写 query / 拆解子查询 / 元数据过滤 | RAGSelfCorrector.CorrectRetrieval |
| 召回低质 | low_quality_hits 累计 ≥ 3 | 语料降权 50% | RAGSelfCorrector.MarkLowQuality |
| 召回噪声 | low_quality_hits 累计 ≥ 10 | 语料归档（从召回池剔除） | RAGSelfCorrector.ArchiveCorpus |
| 生成幻觉 | Faithfulness < 0.7 | 降温 + 强制引用 + 重新生成（最多 3 次） | LLMSelfCorrector.Regenerate |
| 生成跑题 | Answer Relevance < 0.7 | Prompt 重写 + 重新路由 | PromptSelfCorrector.Rewrite |
| 资产包低效 | Asset Effectiveness < 0.3 | 降级为 inactive + 发布 asset.degraded | AssetBundleLearner.Degrade |
| 资产包陈旧 | 30 天 use_count=0 | 自动归档 | AssetBundleLearner.Archive |

**矫正循环**（参考 LangGraph Reflection，MAX_ITERATIONS=3）：
```
for i in 1..3:
    generate()
    score = self_supervise()
    if score > threshold:
        return success
    else:
        apply_correction(based_on_failure_matrix)
return fallback_to_human
```

#### 7.2.3 自我学习（Self-Learning）— 沉淀与迭代

**学习触发**：
- 高 reward 对话（aggregated_reward ≥ 1.5）→ 销冠话术补录到 RAG 知识库
- 高 reward + 转化（reward ≥ 2.0 & outcome=converted）→ 生成资产包候选
- 候选聚类（≥ 3 相似）→ 升级为 A/B 实验
- A/B 收敛（Thompson Sampling ≥ 0.95）→ 自动 promote 候选

**学习闭环**（参考 DSPy Optimizer + Iterative Feedback-Driven RAG）：
```
1. Collect feedback (FeedbackCollector, 已有)
2. Adjust relevance scores (RAGSelfCorrector, 新增)
3. Fine-tune index (knowledge_corpus 更新, 新增)
4. Generate candidates (AssetBundleLearner, 新增)
5. A/B test (BanditAllocator, 已有)
6. Promote or rollback (AssetBundleLearner, 新增)
```

### 7.3 资产包的自我监督（扩展，不只是 RAG）

用户明确要求"不管是知识库还是资源包"都要支持三位一体。资产包的自我监督设计：

#### 7.3.1 资产包 5 维监督指标

| 维度 | 指标 | 计算方式 |
| --- | --- | --- |
| 使用频次 | UseCount / day | `asset_bundles.use_count` 增量 |
| 用户评分 | Rating 均值 | `asset_bundles.rating` |
| 转化贡献 | reward_when_used / use_count | 关联 `feedback_signals` |
| 召回命中 | Asset Hit Rate | 资产包被 WeaveForRequest 命中的比例 |
| 版本健康 | Version Staleness | 当前版本距上次更新的天数 |

#### 7.3.2 资产包矫正策略

| 场景 | 触发条件 | 修复动作 |
| --- | --- | --- |
| 低效资产包 | 转化贡献 < 0.3 且 use_count ≥ 50 | 降级 inactive |
| 陈旧资产包 | Version Staleness > 90 天 | 标记 stale，触发自我学习生成新候选 |
| 低评分资产包 | Rating < 2.0 且 RatingCount ≥ 50 | 降级 + 触发 A/B 测试新候选 |
| 高效资产包 | 转化贡献 ≥ 1.0 且 use_count ≥ 100 | 标记 champion，扩大流量 |

#### 7.3.3 资产包自我学习闭环

```
高 reward 对话 → ChampionDialogueAnalyzer 提取话术
                → 打包为 AssetBundle 候选（status=draft）
                → 候选聚类（pgvector similarity ≥ 0.85）
                → 升级为 A/B 实验（BanditAllocator 流量分配）
                → 收敛后自动 promote（status=active）
                → 原 baseline 降级（status=inactive）

低效资产包    → 自动降级
              → 触发自我学习生成新候选
              → 形成闭环
```

### 7.4 全自动开关设计

用户要求"用户开启就要全自动执行"。设计如下：

#### 7.4.1 三级开关矩阵

| 开关级别 | 配置项 | 默认值 | 控制范围 |
| --- | --- | --- | --- |
| **总开关** | `self_learning.enabled` | false | 整个三位一体机制 |
| **能力开关** | `self_learning.rag.enabled` | false | RAG 自我监督/矫正/学习 |
| **能力开关** | `self_learning.asset_bundle.enabled` | false | 资产包三位一体 |
| **强度开关** | `self_learning.autonomy_level` | "manual" | manual / supervised / autonomous |

#### 7.4.2 三级自治等级（参考自动驾驶 L0-L5）

| 等级 | 名称 | 行为 |
| --- | --- | --- |
| L0 | manual | 仅采集信号，不执行任何矫正/学习动作；所有变更需人工审批 |
| L1 | supervised | 自动执行矫正（降权/归档/重写），但学习动作（候选生成/A/B promote）需人工审批 |
| L2 | autonomous | 全自动：矫正 + 学习 + A/B + promote 全部自动执行；仅"重大变更"（资产包下线）落告警 |

### 7.9 头脑风暴二次论证（针对扩展设计）

#### 7.9.1 多视角评估

| 视角 | 优势 | 风险 | 对策 |
| --- | --- | --- | --- |
| 性能 | 5 维监督全异步，主链路 < 5ms | LLM-as-Judge 调用增加 LLM 成本 | 仅对 10% 流量采样做 LLM-as-Judge；其余用规则评分 |
| 可靠性 | 失败矩阵覆盖 7 类场景 | 矫正动作可能误判 | L1+ 等级下矫正动作需落库可回滚；L2 下熔断机制兜底 |
| 安全 | 三级自治等级 + 6 道护栏 | autonomous 等级下可能 promote 错误候选 | BanditAllocator 收敛阈值 0.95 + 24h 预警 + 看板 reject |
| 成本 | 复用现有 feedback_loop 90% 代码 | LLM-as-Judge 增加 token 消耗 | 用本地小模型做 Judge（如 qwen2.5-7b）；仅复杂场景调云端 |
| 渐进式 | 三级开关支持渐进上线 | 用户可能不理解等级差异 | 看板提供"等级说明" tooltip + 默认 manual 等级 |

#### 7.9.2 与同行设计的差异化优势

| 维度 | 同行（LangGraph/Closed-Loop RAG） | 我们的设计 |
| --- | --- | --- |
| 触发时机 | 多为请求级同步循环 | 对话级异步事件 + 定时 cron 双驱动 |
| 评估方式 | LLM-as-Judge 全量 | 10% 采样 LLM-as-Judge + 90% 规则评分（成本优化） |
| 学习对象 | 仅 RAG 语料 | RAG 语料 + 资产包（双学习对象） |
| 自动化程度 | 多为半自动（需人工审批） | 三级自治（manual/supervised/autonomous） |
| 安全机制 | 主要是 retry 上限 | 6 道护栏 + 熔断 + 24h 预警 + 看板回滚 |
| 复用程度 | 从零搭建 | 100% 复用 feedback_loop / event / async 基础设施 |

#### 7.9.3 风险与对策（扩展）

| 风险 | 对策 |
| --- | --- |
| LLM-as-Judge 本身幻觉 | Judge 模型用低 temperature(0.0) + 多次投票（3 次取多数） |
| 矫正动作雪崩 | 每日矫正上限 1000 次 + 失败率 > 30% 自动熔断到 supervised |
| autonomous 等级下 promote 错误候选 | BanditAllocator 收敛阈值 0.95 + 7 天观察期 + 看板一键 rollback |
| 资产包自我学习污染现役资产包 | 候选 status=draft，必须 A/B 收敛才 promote；原 baseline 保留为 inactive 可回滚 |
| 自我监督信号被刷单 | 单 session 限 1 条监督信号 + 异常 IP 检测 + 看板可标记"刷单"撤销 |

## 八、总结

本设计文档（v1.1）在 v1.0 基础上扩展为**三位一体 + 全自动开关**机制：

1. **三位一体**：自我监督（5 维指标 + LLM-as-Judge）→ 自我矫正（失败矩阵 + 7 类修复策略）→ 自我学习（语料补录 + 资产包 A/B 迭代）
2. **双对象**：RAG 知识库 + 资产包，两者均有完整的三位一体闭环
3. **全自动开关**：三级自治等级（manual / supervised / autonomous）+ 6 道安全护栏 + 熔断机制
4. **同行参考**：采纳 Self-RAG / CRAG / SH-RAG / LangGraph Reflection / DSPy / Closed-Loop RAG / Self-Improving Agentic RAG 七大业界设计的精华
5. **100% 复用**：现有 feedback_loop / event / async / BanditAllocator 基础设施全部复用，新增代码集中在监督 + 矫正 + 开关三块

用户启用 `autonomous` 等级后，整个机制即全自动运行：对话开始即触发 RAG 预热，对话结束即触发反思 + 候选生成，定时任务驱动 A/B 测试与自动上下线，全程落库可观测，6 道护栏防雪崩，看板支持一键回滚。
