## 一、摘要

本论文论证 HiveMTK 项目中「资产包（AssetBundle）」与「知识库（KnowledgeBase / RAG）」两个核心模块的职责划分与边界。结合项目代码（model / service / self_learning 三层佐证）和行业案例（OpenAI GPTs、Coze、Dify、LangChain、LlamaIndex、MCP、Salesforce Einstein、ServiceNow Now Assist、Microsoft Copilot Studio 等 10+ 平台）得出结论：

1. **资产包**：解决「**怎么回答**」的问题，是输出层的 prompt 模板资产，100% 遵守 OpenAI ChatML 协议，通过 Weave 织布算法与 RAG 召回、对话历史拼装为最终 prompt。
2. **知识库**：解决「**答什么**」的问题，是输入层的检索语料资产，由文档→切片→向量化→检索（BM25 + pgvector 混合）构成 RAG 管道。
3. **边界划分**：以「**调用控制方**」与「**内容形态**」双维度划分——资产包是「应用控制、模板形态」的输出资产，知识库是「应用注入、语料形态」的输入资产，与 MCP 协议中 Tools/Resources 的边界一致。
4. **协同而非互斥**：两者在运行时通过 Weave 织布算法协同，在自我学习中通过 `dialogue.ended` 事件协同（销冠对话同时触发语料补录与候选资产包生成）。

## 二、概念定义

### 2.1 资产包（AssetBundle）

**项目定义**（来自 [asset_bundle.go:L1-L17](file:///Users/xiaofang/Documents/www/go/hivemtk/hivemtk/user-server/internal/model/asset_bundle.go#L1-L17)）：

> 资产包 = 100% 遵守 OpenAI messages 协议的 JSON 数组
> 后端用 GORM JSONB 存储 messages 数组
> Weave 织布算法动态拼装最终 prompt（资产包 + RAG + 历史 + 当前问题）

**核心特征**：
- **协议合规**：messages 数组每条 `{role, content, tool_call_id?, name?}` 完全对齐 OpenAI ChatML，可直接喂给任何兼容 OpenAI 协议的 LLM
- **可分发**：通过 Scope（private/shared/official）+ 蜂巢商城上架，形成跨租户分发
- **可版本化**：Version 字段 + AssetBundleVersionLog 表支持语义化版本
- **可计量**：UseCount / Rating / RatingCount 字段驱动自我学习
- **可热插拔**：WeaveForRequest 运行时按 Scope/Status 过滤，无需重启

### 2.2 知识库（KnowledgeBase / RAG）

**项目定义**（来自 [knowledge_workspace.go:L28-L84](file:///Users/xiaofang/Documents/www/go/hivemtk/hivemtk/user-server/internal/aiagent/knowledge/model/knowledge_workspace.go#L28-L84)）：

> KnowledgeDocument（产品维度文档）→ KnowledgeChunk（切片）→ EmbeddingID/SimilarityScore → 检索召回

**核心特征**：
- **三层结构**：Document（原始文档）→ Chunk（切片单元）→ Embedding（向量），符合 RAG 标准管道
- **多源接入**：SourceType 支持 upload/text/url/batch/openapi 五种数据源
- **混合检索**：rag_searcher_vector.go + rag_searcher_bm25.go 实现 pgvector + BM25 混合检索
- **可观测**：KnowledgeSearchLog 记录每次检索的 QueryHash / TopK / MaxScore / Latency / Hit
- **可治理**：KnowledgeImportLog 提供导入审计；self_learning 模块支持 chunk 质量评分与降权/归档

### 3.5 两者在自我学习机制中的分工

项目把自我学习设计为「三位一体闭环」（自我监督 → 自我矫正 → 自我学习），资产包与知识库各自拥有独立的监督器与矫正器：

| 维度 | 知识库（RAG 侧） | 资产包（AssetBundle 侧） |
| --- | --- | --- |
| 监督器 | RAGSelfSupervisor | AssetBundleSelfSupervisor |
| 矫正器 | RAGSelfCorrector | AssetBundleLearner |
| 监督指标（5 维） | recall_precision / recall_coverage / generation_fidelity / answer_relevance / asset_effectiveness（共享） | asset_adoption / asset_conversion / asset_complaint / asset_freshness / asset_ab_converge |
| 矫正触发 | dialogue.started（Warmup）+ dialogue.ended（Reflect） | dialogue.ended（GenerateCandidate）+ cron（ClusterUpgrade / CheckConvergence / DegradeInactiveAssets） |
| 矫正动作 | retrieve_retry / query_rewrite / chunk_archive / chunk_champion_upsert | candidate_generate / cluster_upgrade / ab_test / promote / rollback / degrade |
| 学习沉淀 | 销冠对话 → knowledge_chunks（source=dialogue_extract, quality=champion） | 销冠对话 → asset_bundle_candidates（status=candidate）→ A/B → active |

关键代码位置：
- RAGSelfCorrector 职责注释：[rag_self_corrector.go:L1-L26](file:///Users/xiaofang/Documents/www/go/hivemtk/hivemtk/user-server/internal/service/self_learning/rag_self_corrector.go#L1-L26)
- AssetBundleLearner 职责注释：[asset_bundle_learner.go:L1-L29](file:///Users/xiaofang/Documents/www/go/hivemtk/hivemtk/user-server/internal/service/self_learning/asset_bundle_learner.go#L1-L29)
- RAGSelfSupervisor 5 维指标：[rag_self_supervisor.go:L9-L22](file:///Users/xiaofang/Documents/www/go/hivemtk/hivemtk/user-server/internal/service/self_learning/rag_self_supervisor.go#L9-L22)
- AssetBundleSelfSupervisor 5 维指标：[asset_bundle_self_supervisor.go:L9-L23](file:///Users/xiaofang/Documents/www/go/hivemtk/hivemtk/user-server/internal/service/self_learning/asset_bundle_self_supervisor.go#L9-L23)

**关键协同点**：
1. `asset_effectiveness` 指标由 RAGSelfSupervisor 采集，但作为资产包的综合反馈维度，是两者的「共享信号」
2. 销冠对话（reward ≥ 1.5）同时触发：知识库补录（chunk_champion_upsert）+ 资产包候选生成（GenerateCandidate）
3. 两者都通过 SelfCorrectionDispatcher 派发修复策略，受 SwitchService 三级自治等级（manual/supervised/autonomous）统一管控

## 四、职责边界对比矩阵

| 维度 | 资产包（AssetBundle） | 知识库（KnowledgeBase / RAG） |
| --- | --- | --- |
| **解决的核心问题** | 「怎么回答」——回答的风格、话术、SOP、 objections 处理 | 「答什么」——事实、产品信息、FAQ、历史对话 |
| **内容形态** | 结构化 messages 数组（OpenAI ChatML） | 非结构化文本切片 + 向量 |
| **协议合规** | 100% OpenAI ChatML，可跨 LLM 厂商 | 项目自有 schema，通过 RAG 引擎抽象 |
| **生产方式** | 人工编辑 + 自我学习候选生成（ChampionAnalyzer 提取话术） | 文档上传 + OpenAPI 同步 + 销冠对话补录 |
| **更新频率** | 中频（A/B 周期 7 天，自动 promote） | 高频（dialogue.ended 即可补录） |
| **版本管理** | 语义化版本 + VersionLog | 文档级 EmbedStatus + Chunk ContentHash |
| **分发机制** | Scope（private/shared/official）+ 蜂巢商城 | ProductID 多租户隔离，无跨租户分发 |
| **计量字段** | UseCount / Rating / RatingCount | SearchCount / HitCount / SimilarityScore |
| **运行时角色** | 输出层模板（被 WeaveForRequest 拼装到最终 prompt） | 输入层检索（被 RAG 引擎召回后注入 messages） |
| **自我学习触发** | reward ≥ 1.5 & outcome=converted | reward ≥ 1.5（补录）或 reward ≤ -1.0（降权） |
| **自我学习产物** | asset_bundle_candidates → A/B → active/inactive | knowledge_chunks（quality=champion/low_quality/archived） |
| **失败模式** | 资产包陈旧 / 低效 / 低评分 | 召回失败 / 召回低质 / 召回噪声 / 生成幻觉 / 生成跑题 |
| **修复策略** | degrade / archive / generate new candidate / A/B | retrieve_retry / query_rewrite / chunk_archive / chunk_champion_upsert |
| **行业对标** | OpenAI GPTs Instructions / Coze Bot Prompt / Dify Prompt 模板 | OpenAI GPTs Knowledge / Coze 知识库 / Dify Knowledge Base |
| **MCP 协议归类** | Prompts（参数化提示词模板） + 部分 Tools（若含 tool_calls） | Resources（应用注入的上下文数据） |

### 5.2 MCP 协议的三分法（行业最严谨边界）

MCP（Model Context Protocol，Anthropic 主导，2024-11 开源）明确三类资产：

| 资产类型 | 职责 | 控制方 | HiveMTK 对应 |
| --- | --- | --- | --- |
| **Tools** | LLM 可调用的函数，有副作用 | 模型控制（model-controlled） | tooluse 包（12 层装饰器） |
| **Resources** | LLM 可读取的上下文数据，只读 | 应用控制（application-controlled） | **知识库（KnowledgeBase / RAG）** |
| **Prompts** | 可复用的提示词模板，参数化 | 用户控制（user-controlled） | **资产包（AssetBundle）** |

**关键启示**：MCP 把「知识」归入 Resources 而非 Tools，把「提示词模板」单列为 Prompts。HiveMTK 的资产包因 100% 遵守 OpenAI ChatML 协议（messages 数组即提示词模板），本质上对应 MCP 的 Prompts；知识库对应 MCP的 Resources。这是行业里第一次用协议层把两者切清楚。

参考链接：
- [MCP 官网](https://modelcontextprotocol.io/)
- [MCP 规范仓库](https://github.com/modelcontextprotocol/specification)
- [MCP Concepts](https://modelcontextprotocol.io/docs/concepts/architecture)

### 5.3 企业级案例对标

#### 案例 1：Salesforce Einstein 1 — 结构化 vs 非结构化

- **资产/工具职责**：Einstein Copilot Actions 暴露 CRM 业务能力（创建商机、查询客户），Action = 工具资产
- **知识库职责**：Data Cloud + Vector Search 检索非结构化知识（PDF、邮件、聊天记录）
- **边界判例**：Salesforce 明确把「结构化业务数据查询」归为 Action 而非知识库——因为 CRM 数据有时效性且需事务一致，不应入向量库
- **参考**：[Salesforce Einstein 文档](https://help.salesforce.com/s/articleView?id=sf.einstein_copilot.htm)

#### 案例 2：ServiceNow Now Assist — 方案 vs 执行

- **资产/工具职责**：Workflow + Integration Hub 暴露 ITSM 动作（建工单、派单、改状态）
- **知识库职责**：Now Assist 知识库检索 ServiceNow Knowledge Base（ITIL 知识文章）
- **边界判例**：ServiceNow 强调「知识用于回答用户怎么解决，动作用于替用户解决」——同一问题可能先 RAG 给方案，再 Action 执行，形成「知识 → 动作」链路
- **参考**：[ServiceNow Now Assist](https://www.servicenow.com/products/nowassist.html)

#### 案例 3：Microsoft Copilot Studio — 三元结构

- **资产/工具职责**：Plugins / Connectors 接入 Power Platform 连接器（500+ SaaS）
- **知识库职责**：Knowledge sources 接入 SharePoint、OneDrive、网站、自定义文档
- **第三类资产**：Topic（声明式对话流），与 MCP 的 Prompts 对齐
- **边界判例**：Copilot Studio 明确把「Knowledge」与「Actions/Plugins」作为 Bot 配置的两个独立 tab；Generative Answers（RAG）与 Generative Actions（Function Calling）是两条独立管线
- **参考**：[Microsoft Copilot Studio 文档](https://learn.microsoft.com/microsoft-copilot-studio/)

#### 案例 4：LlamaIndex Agentic RAG — 知识库即工具

- LlamaIndex 把多个 Index（知识库）包装为多个 `QueryEngineTool`，由 Agent 路由
- 这是「知识库即只读工具」的工程化范例，与 HiveMTK 「资产包 + RAG 通过 Weave 协同」的思路互补
- **参考**：[LlamaIndex Agentic RAG](https://docs.llamaindex.ai/en/stable/optimizing/production_rag/)

### 5.4 HiveMTK 与行业对照定位

| 维度 | 行业主流（GPTs/Coze/百炼） | HiveMTK |
| --- | --- | --- |
| 工具/动作抽象 | function calling / OpenAPI 插件 | tooluse 包 12 层装饰器（独立模块） |
| 知识库抽象 | 文档 + 切片 + 向量 | KnowledgeDocument + KnowledgeChunk + pgvector/BM25 混合 |
| 提示词模板抽象 | GPTs Instructions / Coze Bot Prompt | **AssetBundle（messages JSONB）** |
| 三者关系 | 多为二分（工具 vs 知识） | 三分（tooluse 工具 + 知识库 Resources + 资产包 Prompts），与 MCP 对齐 |
| 自我学习覆盖 | 多为 RAG 单侧 | RAG + 资产包双侧三位一体 |

**HiveMTK 的差异化定位**：资产包不是「工具」也不是「知识库」，而是独立的「提示词模板资产」——这一设计与 MCP Prompts、Microsoft Copilot Studio Topic、GPTs Instructions 同类，但 HiveMTK 进一步把资产包做成了「可上架、可计费、可 A/B、可自我学习」的完整商品，是行业里少数把 Prompts 资产化到如此深度的实现。

## 六、边界争议点与处理建议

### 6.1 RAG 是知识库还是工具？

- **行业争议**：「知识库派」（Coze/百炼）把 RAG 归知识库；「工具派」（LlamaIndex）把 RAG 包装为 QueryEngineTool
- **MCP 裁决**：数据是 Resource，检索是 Tool——存储层归知识库，调用层归工具
- **HiveMTK 实践**：RAG 引擎（aiagent/rag/）是独立的 L4 能力层模块，知识库（aiagent/knowledge/）是 L2 业务层模块；RAG 引擎可被 WeaveForRequest 调用，也可被自我学习协程调用，本质是「能力」而非「资产」
- **建议**：保持当前划分——RAG 引擎是能力，知识库是资产，两者不混同

### 6.2 函数调用返回结果是否沉淀为知识？

- **行业现状**：GPTs/Coze/Dify/LangChain 均不自动沉淀 tool 返回值到知识库
- **HiveMTK 实践**：tooluse 包的 AuditDecorator 落库调用日志，但不沉淀到 knowledge_chunks；销冠对话补录走 RAGSelfCorrector.Reflect 路径，源头是对话本身而非工具返回
- **建议**：保持当前「工具结果不沉淀为知识」的设计，避免时效性数据污染知识库

### 6.3 工具的使用说明放哪？

- **行业共识**：短说明进工具元数据（description），长说明进知识库 RAG
- **HiveMTK 实践**：资产包的 Title/Description/Tags 是元数据；资产包的 messages 数组本身就是「使用说明的内化」——把 SOP、objections handling、closing 话术直接写成 messages，而非外挂文档
- **建议**：资产包的 messages 即「内化的使用说明」，无需额外知识库存储；tooluse 包的工具描述走 description 字段

### 6.4 自我学习时，知识库纠错和资产包纠错的差异

| 维度 | 知识库纠错 | 资产包纠错 |
| --- | --- | --- |
| 纠错对象 | chunk 内容、向量索引、quality_label | messages 数组、Scope/Status |
| 触发信号 | recall_precision/recall_coverage/generation_fidelity/answer_relevance | asset_adoption/asset_conversion/asset_complaint/asset_freshness/asset_ab_converge |
| 纠错方式 | chunk_archive / chunk_champion_upsert / query_rewrite / retrieve_retry | candidate_generate / cluster_upgrade / ab_test / promote / rollback / degrade |
| 时效性 | 慢周期（chunk 归档需累计 10 次低质命中） | 中周期（A/B 7 天 + 30 天降级检查） |
| 风险 | 错误 chunk 持续误导召回 | 错误资产包导致全量对话风格跑偏 |
| 责任模块 | RAGSelfSupervisor + RAGSelfCorrector | AssetBundleSelfSupervisor + AssetBundleLearner |

**关键差异**：知识库纠错是「内容治理」问题，资产包纠错是「策略治理」问题。HiveMTK 通过两套独立的监督器+矫正器避免混淆，是正确的设计。

## 七、结论与建议

### 7.1 论证结论

1. **职责清晰**：资产包解决「怎么回答」（输出层模板），知识库解决「答什么」（输入层语料），两者通过 Weave 织布算法在运行时协同，边界清晰。
2. **行业对齐**：HiveMTK 的资产包对应 MCP Prompts + Microsoft Copilot Studio Topic + GPTs Instructions；知识库对应 MCP Resources + 行业通用 RAG。这是行业里最严谨的三分法。
3. **自我学习对称**：两者均拥有独立的「监督器 + 矫正器 + 学习器」三位一体闭环，且通过 SwitchService 三级自治等级统一管控，设计对称且可控。
4. **协同而非互斥**：销冠对话同时触发知识库补录与资产包候选生成，是协同设计；asset_effectiveness 指标共享，是耦合点而非冲突点。

### 7.2 实践建议

| 建议 | 优先级 | 说明 |
| --- | --- | --- |
| 保持资产包 messages 协议合规 | P0 | 任何扩展不得破坏 OpenAI ChatML 协议，否则失去跨 LLM 厂商能力 |
| 保持知识库 RAG 管道独立 | P0 | RAG 引擎是 L4 能力层，知识库是 L2 业务层，两者不可合并 |
| 资产包不上架 KnowledgeChunk | P1 | 资产包的 messages 是模板，不应作为检索语料入库，避免混淆 |
| 知识库不存储 messages 数组 | P1 | 知识库的 chunk 是事实语料，不应存储结构化 prompt 模板 |
| 自我学习开关分域控制 | P1 | `self_learning.rag.enabled` 与 `self_learning.asset_bundle.enabled` 独立开关，允许用户单侧启用 |
| 资产包计费与知识库计费分离 | P2 | 资产包按 Price + UseCount 计费；知识库按 SearchCount + TokenCount 计费，不可混用 |
| 监督指标扩展时保持边界 | P2 | 新增监督指标需明确归属（RAG 侧 or 资产包侧），asset_effectiveness 是允许的共享指标，但不应泛滥 |

### 7.3 不应混淆的边界（红线）

1. **资产包不应直接调用 LLM**：资产包是 prompt 模板，由 WeaveForRequest 拼装后交给 LLM；资产包本身不含 LLM 调用逻辑
2. **知识库不应直接产生 messages**：知识库返回 chunks，由 Weave 算法包装为 `role=system` 或 `role=tool` 的 messages
3. **资产包不应存储向量**：资产包是 JSONB messages，不参与向量检索
4. **知识库不应存储 messages 数组**：知识库是 chunk + embedding，不存储 OpenAI ChatML 结构
5. **两者自我学习产物不可互换**：资产包候选不可写入 knowledge_chunks；销冠对话补录的 chunk 不可写入 asset_bundle_candidates

## 九、总结

本论证通过「项目代码佐证 + 行业案例对标 + 头脑风暴边界分析」三重视角，确认了 HiveMTK 项目中资产包与知识库的职责边界：

- **资产包** = 输出层提示词模板资产（OpenAI ChatML messages JSONB），对应 MCP Prompts
- **知识库** = 输入层检索语料资产（Document → Chunk → Embedding），对应 MCP Resources
- **工具** = 独立的 tooluse 包（12 层装饰器），对应 MCP Tools

三者共同构成 HiveMTK 的「AI Agent 三类资产」体系，与 MCP 协议三分法完全对齐，是行业里少数把 Prompts 资产化到「可上架、可计费、可 A/B、可自我学习」深度的实现。两者在自我学习机制中拥有对称的三位一体闭环（监督 → 矫正 → 学习），通过 SwitchService 三级自治等级统一管控，设计严谨、边界清晰、协同而非互斥。

### 10.5 计费模型字段归属审计详情（2026-07-25 二轮）

**审计对象**：
- `usage_reports` 表（平台侧资产包用量计费，user-server 通过 platform_api_client 上报）
- `llm_routing_logs` 表（本地 LLM 调用计费，user-server 落库）

**字段归属分离验证**：

| 维度 | usage_reports（资产包计费） | llm_routing_logs（LLM 计费） |
| --- | --- | --- |
| 计费键 | asset_id + request_id 幂等 | trace_id + scenario |
| 用量字段 | use_count / reported_use_count | prompt_tokens / completion_tokens / total_tokens |
| 成本字段 | Price（资产包定价） | prompt_cost / completion_cost / total_cost |
| 归属模型 | LocalAsset（user-server）+ 平台侧 usage_reports 表 | LogEntry（llm 包内）+ llm_routing_logs 表 |
| 上报路径 | user-server → platform API → usage_reports | user-server 本地 DB 直写 |

**结论**：两类计费字段归属完全分离，无混用。
