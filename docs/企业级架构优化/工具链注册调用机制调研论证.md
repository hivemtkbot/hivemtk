# 工具链注册调用机制调研论证

## 摘要

工具链（Tool Chain）是 Agent 系统连接大语言模型与外部业务能力的中枢神经，其注册机制、调用契约、可观测性与容错策略直接决定了 Agent 系统的工程成熟度与企业级可用性。HiveMTK 作为面向私域营销与客服场景的 Go 语言 Agent 平台，在 `internal/aiagent/agent/tooluse/` 单包内沉淀了 41 个业务工具、8 层装饰器链、单例注册中心、LLM Function Calling 调度器与白名单权限模型，并通过 `portcontract` 包打破 service ↔ tooluse 的 import cycle，在工程化层面已显著领先多数开源方案。

本报告横向调研 OpenAI Agents SDK、LangChain/LangGraph、CrewAI、Microsoft AutoGen v0.4、Google ADK、Anthropic MCP、langchaingo、CloudWeGo Eino 等 8 个主流开源 Agent 工具链机制，与 HiveMTK 现有实现进行多维度对比，识别出 HiveMTK 在装饰器链完整性、五层架构合规性、权限与熔断内建等维度的优势，同时指出 Schema 手写、无流式工具、无 MCP 协议、ToolRouter 未装配、审计内存版等关键短板。基于此，本报告按 P0/P1/P2/P3 四级优先级提出 13 项优化建议，并给出实施风险与回滚预案。

核心结论：**HiveMTK 工具链机制在企业级容错与架构合规维度具备显著优势，但在开发者体验（DX）、生态开放性（MCP）、异步与流式能力、可观测性闭环方面需要补齐；建议本迭代优先落地 ToolRouter 装配与 HTTP 调试 API，下迭代推进流式工具与 DB 审计，季度内完成 MCP 适配。**

## 一、调研范围与方法

### 1.1 调研范围

本调研覆盖两条主线：

1. **开源主流 Agent 工具链机制**：选取 Python 生态 5 个（OpenAI Agents SDK、LangChain/LangGraph、CrewAI、AutoGen v0.4、Google ADK）、协议层 1 个（Anthropic MCP）、Go 生态 2 个（langchaingo、Eino），共计 8 个具有代表性的开源方案。
2. **HiveMTK 自研工具链机制**：覆盖 `internal/aiagent/agent/tooluse/`、`internal/aiagent/agent/portcontract/`、`internal/router/` 中与工具注册、调用、装饰、装配、权限管理相关的全部代码资产。

### 1.2 调研方法

- **静态代码分析**：直接阅读 HiveMTK 源码，提取核心抽象、注册流程、装饰器链顺序、装配入口与权限模型。
- **官方文档比对**：对照各开源框架的官方文档与 GitHub 仓库 README，提取其工具注册方式、Schema 生成机制、错误处理策略、可观测性能力。
- **维度化对比**：以"注册方式 / Schema 生成 / 装饰器链 / 流式工具 / 异步原生 / 错误回传 / 权限控制 / 熔断 / 限流 / 重试 / Tracing / 取消支持 / 跨语言 / 解耦部署 / Import cycle / 五层架构合规"16 个维度构造横向对比矩阵。
- **风险驱动论证**：基于差距分析推导优化优先级，并对每项优化给出风险与回滚预案。

### 1.3 调研边界

本调研不涉及：
- 具体业务工具（如 `customer.search`、`reach.sms.send`）的业务逻辑实现细节；
- LLM 模型本身的选型与调用；
- Agent Loop 上层策略（如 ReAct 推理、Planning）；
- 前端可视化与配置 UI。

## 二、主流开源 Agent 工具链机制综述

### 2.1 OpenAI Agents SDK（Python）

OpenAI Agents SDK 是 OpenAI 官方推出的轻量级 Agent 框架，其工具链机制以"开发者体验优先"为核心理念。

**工具注册方式**：

```python
from agents import function_tool, FunctionTool

@function_tool
def search_customer(customer_id: str) -> dict:
    """根据客户 ID 查询客户信息。

    Args:
        customer_id: 客户唯一标识
    """
    # ...
    return {"id": customer_id, "name": "张三"}
```

`@function_tool` 装饰器从 Python 函数的类型注解（type hints）+ docstring 出发，借助 Pydantic V2 自动生成 JSON Schema，无需开发者手写。对于无法用装饰器覆盖的场景（如动态构造工具），可使用 `FunctionTool(name, description, params_json_schema, on_invoke_tool)` 手动构造，`params_json_schema` 为标准 JSON Schema 字典。

**调用循环**：`Runner.run()` 自动执行 tool_call → 参数校验 → 调用工具 → tool_result 回灌模型 → 直到模型不再发起 tool_call 或触发 `max_turns`。该循环对开发者完全透明。

**错误处理**：工具抛出的异常默认被 Runner 捕获并作为 tool_result（含错误信息）回传给模型，模型可基于错误进行自我纠错；通过 `tool_use_behavior` 参数可自定义行为（如 `stop_on_first_error`）。

**可观测性**：内置 tracing，与 OpenTelemetry 兼容，支持自动记录每次 tool_call 的输入、输出、耗时与异常堆栈。

### 2.2 LangChain / LangGraph

LangChain 是 Python LLM 应用生态事实标准，LangGraph 是其状态图引擎，二者工具链机制高度耦合。

**三种工具构造方式**：

```python
from langchain_core.tools import tool, StructuredTool, BaseTool
from pydantic import BaseModel, Field

# 方式 1：装饰器
@tool
def search_customer(customer_id: str) -> dict:
    """根据客户 ID 查询客户信息。"""
    ...

# 方式 2：StructuredTool.from_function
class SearchInput(BaseModel):
    customer_id: str = Field(description="客户唯一标识")

search_tool = StructuredTool.from_function(
    func=search_customer,
    name="search_customer",
    description="根据客户 ID 查询客户信息",
    args_schema=SearchInput,
)

# 方式 3：BaseTool 子类
class SearchCustomerTool(BaseTool):
    name: str = "search_customer"
    description: str = "根据客户 ID 查询客户信息"
    args_schema: type[BaseModel] = SearchInput

    def _run(self, customer_id: str) -> dict:
        ...
```

三种方式均依赖 Pydantic V2 `args_schema` 自动生成 JSON Schema。

**LangGraph ToolNode**：作为 LangGraph 节点，`ToolNode` 接收模型返回的多个 tool_call 并并行执行，结果以 `ToolMessage` 形式回灌。`InjectedState` / `InjectedToolArg` 注解允许开发者向工具注入 LangGraph state 中特定字段而不暴露给 LLM（如用户 ID、会话上下文）。

**错误处理**：`handle_tool_error=True` + `ToolException` 机制，工具抛出 `ToolException` 时错误内容会被回传给模型，模型可据此纠错；其他异常则直接抛出。

**可观测性**：LangSmith（商业产品）与 Langfuse（开源）提供端到端 trace。

### 2.3 CrewAI

CrewAI 定位于多 Agent 协作场景，工具机制相对轻量。

```python
from crewai_tools import tool

@tool("Search Customer Tool")
def search_customer(customer_id: str) -> dict:
    """根据客户 ID 查询客户信息。"""
    ...
```

`@tool("Name")` 装饰器语法与 LangChain 几乎一致；同时也支持 `BaseTool` 子类与 `StructuredTool.from_function`。工具通过 `tools=[...]` 列表直接传给 `Agent(tools=[...])`。

**错误处理**：异常被 Crew 循环捕获并记录到日志，但**不强制回传模型**，模型可能在不知情的情况下继续推理。这是 CrewAI 与 LangChain/OpenAI SDK 的关键差异。

### 2.4 Microsoft AutoGen v0.4

AutoGen v0.4 是微软重写的多 Agent 对话框架，工具机制强调异步与取消。

```python
from autogen_core import FunctionTool, CancellationToken

async def search_customer(customer_id: str) -> dict:
    """根据客户 ID 查询客户信息。"""
    ...

tool = FunctionTool(search_customer, description="...")
result = await tool.run_json({"customer_id": "C001"}, CancellationToken())
```

直接传普通函数即可被自动包装为 `FunctionTool`；如需更强控制力，可继承泛型基类 `BaseTool[Args, Return]`，强制实现 async `run` 方法。

**特色能力**：`CancellationToken` 贯穿整个调用链，支持长任务取消——这是 AutoGen 区别于其他 Python 框架的标志性能力。

**可观测性**：OpenTelemetry 原生集成，trace/span 自动注入。

### 2.5 Google ADK

Google Agent Development Kit（ADK）主打"函数即工具"的极简范式。

```python
from google.adk.tools import tool, ToolContext

@tool
def search_customer(customer_id: str, tool_context: ToolContext) -> dict:
    """根据客户 ID 查询客户信息。"""
    state = tool_context.state
    # 通过 ToolContext 访问会话状态、artifacts、权限检查
    ...
```

`ToolContext` 是 Google ADK 的核心抽象，提供：会话状态读写、artifacts 文件存储、权限检查回调、回调进入下一步前的钩子。

**特色能力**：
- 内置 `BuiltInCodeExecution` 沙箱，模型可直接生成并执行代码；
- `LongRunningTool` 抽象支持异步任务 + 人工确认钩子，适合工作流类场景；
- 原生 MCP 客户端，可直接消费 MCP server。

### 2.6 Anthropic MCP（Model Context Protocol）

MCP 是 Anthropic 推出的协议层抽象，与语言无关，基于 JSON-RPC 2.0。

**核心方法**：
- `tools/list`：返回工具列表，每个工具包含 `name`、`description`、`inputSchema`（标准 JSON Schema）；
- `tools/call`：调用工具，参数为 `{name, arguments}`，返回 `{content: [...], isError: bool}`。

**错误语义**：通过 `isError: true` 区分业务错误与协议错误。业务错误（如客户不存在）应返回 `isError: true` 并附错误描述，让模型自我纠错；协议错误（如工具名不存在）则通过 JSON-RPC error 字段返回。

**部署形态**：工具作为独立进程部署（stdio、HTTP、SSE 三种传输），可跨语言复用，被 Claude Desktop、Cursor、Windsurf 等客户端消费。MCP 因此被喻为工具生态的 **"USB-C 接口"**。

**高层封装**：FastMCP 提供 FastAPI 风格的高层 API，开发者用 `@mcp.tool()` 装饰器即可暴露工具为 MCP server，无需手写 JSON-RPC。

### 2.7 Go 生态：langchaingo / Eino

#### langchaingo

langchaingo 是 LangChain 的 Go 移植，工具机制相对简陋：

```go
type Tool interface {
    Name() string
    Description() string
    Call(ctx context.Context, input string) (string, error)
}
```

输入参数是纯字符串，需工具内部自行解析；Schema 需手动构造（通过 `tools.NewTool` 传入 description）。**无装饰器、无权限、无熔断、无限流**，是一个"最小可用"实现。

#### Eino (CloudWeGo)

Eino 是字节跳动 CloudWeGo 开源的 Go Agent 框架，工具机制更接近 HiveMTK：

```go
type BaseTool interface {
    Info(ctx context.Context) (*schema.ToolInfo, error)
    InvokableRun(ctx context.Context, arguments string, opts ...Option) (string, error)
}
```

`Info(ctx)` 返回工具元数据与 JSON Schema，需开发者通过 `schema.NewParamsOneOfByParams` 手动构造；`InvokableRun` 接收 JSON 字符串参数，需工具内部反序列化。OpenTelemetry 原生集成，支持 `ctx.Done()` 取消。

## 三、HiveMTK 本系统工具链机制剖析

### 3.1 代码组织与五层架构归属

HiveMTK 工具链相关代码分布于三个目录：

```
hivemtk/user-server/internal/aiagent/agent/tooluse/      # 工具核心实现包
hivemtk/user-server/internal/aiagent/agent/portcontract/ # Port 契约包（打破 import cycle）
hivemtk/user-server/internal/router/                     # 装配入口与 HTTP API
hivemtk/user-server/internal/service/                   # 业务适配器
```

按 HiveMTK 五层架构（infra / domain / service / router / api）归属：
- **domain 层**：`tooluse.Tool` 接口、`ToolParameters`、`ToolResult`、`ToolCategory`、`ToolContext`；
- **service 层**：`service.tool_ports_adapter.go`（业务 Port 适配器）、`service.sales_engine.go` 中 `AgentToolExecutor` 接口；
- **router 层**：`router.tool_executor_wiring.go`（装配入口）、`router.tool_executor_adapter.go`（适配器）、`router.inference_orchestrator_wiring.go`（权限管理 HTTP API）；
- **infra 层**：`tooluse.MemoryAuditLogger`、`tooluse.MemoryCostTracker`、`tooluse.CircuitBreakerRegistry`、`tooluse.db_audit_persister.go`（雏形）。

### 3.2 核心抽象：Tool 接口 / BaseTool / ToolParameters / ToolResult

核心抽象定义于 `internal/aiagent/agent/tooluse/tool.go`：

```go
type Tool interface {
    Name() string
    Category() ToolCategory
    Description() string
    Parameters() ToolParameters
    Execute(ctx context.Context, args map[string]any) (ToolResult, error)
}

type ToolParameters struct {
    Type       string
    Properties map[string]ToolParam
    Required   []string
}

type ToolResult struct {
    Success    bool
    Data       any
    Error      string
    Timing     ToolTiming
    ToolName   string
    ExecutedAt time.Time
    AuditTrace string
}
```

`BaseTool` 提供通用基类，封装 `name/category/description/parameters` 字段与默认方法实现，业务工具只需嵌入 `BaseTool` 并实现 `Execute` 方法即可。

设计评价：
- **优点**：接口契约清晰，`ToolResult` 内建 `Success/Error/Timing/AuditTrace` 字段，天然支持可观测性与错误回传；
- **缺点**：`args map[string]any` 类型不安全，参数校验需在装饰器层补齐；`ToolResult.Data` 为 `any`，序列化时需反射。

### 3.3 注册中心：ToolRegistry（单例 + 线程安全）

注册中心定义于 `internal/aiagent/agent/tooluse/registry.go`：

```go
type ToolRegistry struct {
    mu    sync.RWMutex
    tools map[string]Tool
}

var (
    globalRegistry     *ToolRegistry
    globalRegistryOnce sync.Once
)

func GetGlobalRegistry() *ToolRegistry {
    globalRegistryOnce.Do(func() {
        globalRegistry = NewToolRegistry()
    })
    return globalRegistry
}
```

提供 API：`Register / Unregister / Get / Has / List / ListByCategory / Count / ToLLMFunctions / ListNames`。

设计要点：
- **单例模式**：`sync.Once` 保证全局唯一注册中心；
- **读写锁**：`sync.RWMutex` 支持并发读、互斥写；
- **重复注册保护**：返回 `ErrToolAlreadyExists`，避免误注册覆盖；
- **LLM 友好**：`ToLLMFunctions()` 直接输出 OpenAI Function Calling 兼容的 JSON Schema 数组。

### 3.4 执行器：ToolExecutor（装饰器链 + handler 缓存）

执行器定义于 `internal/aiagent/agent/tooluse/executor.go`：

```go
type ToolExecutor struct {
    registry    *ToolRegistry
    config      ExecutorConfig
    overrides   map[string]ToolHandler
    handlerCache map[string]ToolHandler  // 工具名 → 装饰器链终点
}
```

`Execute(ExecuteRequest)` 主入口流程：
1. 从 registry 取 `Tool` 实例；
2. 检查 `disabled` 列表（`config.DisabledTools`）；
3. 从 `handlerCache` 取已构造的装饰器链终点，未命中则现场构造；
4. 将 `ToolContext`（含 Permissions、CallerID、TraceID 等）注入 `context.Context`；
5. 调用 handler 链，返回 `ToolResult`。

辅助方法：
- `BatchExecute(requests, parallel bool)`：支持顺序或并发批量执行；
- `DispatchByLLMToolCall(toolCalls)`：接收 OpenAI tool_call 格式，并发调度，结果 4000 字符截断；
- `ListAvailableTools` / `ListAvailableLLMFunctions`：自动排除 disabled 工具。

`handlerCache` 是性能优化关键——装饰器链只在首次调用时构造一次，后续直接复用。

### 3.5 八层装饰器链：权限→限流→熔断→参数校验→重试→超时→审计→计费

装饰器链定义于 `internal/aiagent/agent/tooluse/decorator.go`，顺序严格固定：

```
请求 → Permission → RateLimit → CircuitBreaker → ParamValidator
     → Retry → Timeout → Audit → handler(Tool.Execute)
```

| 顺序 | 装饰器 | 文件 | 职责 |
|------|--------|------|------|
| 1 | `PermissionDecorator` | `permission_whitelist.go` | 从 `ToolContext.Permissions` 校验调用方是否有权调用该工具 |
| 2 | `RateLimitDecorator` | `decorator.go` | `caller_id:tool_name` 维度 TokenBucket 限流 |
| 3 | `CircuitBreakerDecorator` | `circuit_breaker.go` | P2-B 熔断器，连续失败 N 次进入冷却 |
| 4 | `ParamValidatorDecorator` | `param_validator.go` | P2-E 参数校验，必填/类型/枚举 |
| 5 | `RetryDecorator` | `decorator.go` | 指数退避 + 抖动，识别不可重试错误 |
| 6 | `TimeoutDecorator` | `decorator.go` | `goroutine + channel + context.WithTimeout` |
| 7 | `AuditDecorator` | `decorator.go` | 参数脱敏摘要 + Prometheus 指标 |
| 8 | `safeExecute` | `decorator.go` | panic 恢复，避免单工具崩溃影响整个进程 |

**不可重试错误分类**（位于 `RetryDecorator`）：
- `permission_denied`
- `rate_limited`
- `circuit_open`
- `validation_failed`

这四类错误即使重试也必然失败，直接返回；其他错误（如网络抖动、临时不可用）才进入指数退避重试。这是比通用重试策略更精细的设计。

### 3.6 LLM Function Calling 集成：DispatchByLLMToolCall（并发上限 5）

`DispatchByLLMToolCall` 是连接 LLM 与工具链的关键桥梁：

```go
const maxConcurrent = 5

func (e *ToolExecutor) DispatchByLLMToolCall(ctx context.Context, calls []LLMToolCall) ([]LLMToolResult, error) {
    sem := make(chan struct{}, maxConcurrent)
    var wg sync.WaitGroup
    results := make([]LLMToolResult, len(calls))
    for i, call := range calls {
        wg.Add(1)
        sem <- struct{}{}
        go func(idx int, c LLMToolCall) {
            defer wg.Done()
            defer func() { <-sem }()
            // 解析 arguments JSON → 调 Execute → 截断到 4000 字符 → 包装 LLMToolResult
        }(i, call)
    }
    wg.Wait()
    return results, nil
}
```

设计要点：
- **信号量并发上限 5**：防止一次 LLM 返回大量 tool_call 打爆下游服务；
- **结果 4000 字符硬截断**：避免长结果撑爆 LLM 上下文窗口；
- **原始长度提示**：截断时附 `原始结果 N 字符，已截断至 4000 字符` 提示，让模型知晓截断发生。

### 3.12 权限模型：WhitelistPermissionChecker（agent 维度白名单）

权限检查器定义于 `permission_whitelist.go`：

```go
type WhitelistPermissionChecker struct {
    globalWhitelist  map[string]bool  // 全局允许的工具
    agentWhitelist   map[string]map[string]bool  // agent_id → tool_name
    defaultAllow     bool
}

func (c *WhitelistPermissionChecker) Check(agentID, toolName string) bool {
    // 1. 显式 Permissions 含 "*" → 放行
    // 2. globalWhitelist 命中 → 放行
    // 3. agentWhitelist[agentID][toolName] 命中 → 放行
    // 4. 否则 → defaultAllow
}
```

**HTTP 管理 API**（`inference_orchestrator_wiring.go`）：
- `GET/POST/PUT/DELETE /api/agent/tools/permission/default`：默认放行策略
- `GET/POST/PUT/DELETE /api/agent/tools/permission/global`：全局白名单
- `GET/POST/PUT/DELETE /api/agent/tools/permission/agents`：agent 维度白名单

**当前生产装配**：`NoOpPermissionChecker{}`（注释说明"智能体权限在更上层 SalesEngine 把控"）。这是一个安全隐患——上层 SalesEngine 是否真的覆盖了所有权限校验路径，需要专项审计。

## 四、对比论证：本系统 vs 开源方案

### 4.1 优势

**优势 1：装饰器链设计最完整**

HiveMTK 是本调研覆盖的 9 个方案中**唯一**在装饰器层显式实现 8 层链路的方案。OpenAI Agents SDK、LangChain、CrewAI、AutoGen、Google ADK、langchaingo、Eino 均未内建装饰器机制，开发者需自行在业务层补齐权限/限流/熔断/重试。MCP 在协议层提供 `isError` 语义但无运行时容错。

**优势 2：五层架构 + Port 模式打破 import cycle**

HiveMTK 通过 `portcontract` 独立包下沉 Port 接口，使 service 层与 tooluse 层解耦，依赖拓扑单向。开源框架（除 MCP 外）均未考虑此问题，因为它们不假定大型单体工程内的分层约束。

**优势 3：LLM Function Calling 零适配**

`ToLLMFunctions()` 直接输出 OpenAI 兼容 JSON Schema，`DispatchByLLMToolCall` 直接接收 OpenAI tool_call 格式，无需任何适配层即可对接 OpenAI / Claude / 通义 / DeepSeek 等主流模型。

**优势 4：企业级特性齐全**

权限白名单 + Prometheus 指标 + 审计日志 + 计费追踪 + 熔断 + 限流 + 重试，构成完整的企业级容错与可观测性闭环，可直接满足金融、政企客户的合规要求。

**优势 5：不可重试错误分类精细**

将 permission/ratelimit/circuit/validation 四类错误识别为不可重试，避免无效重试放大故障，是比通用指数退避更工程化的设计。

**优势 6：panic 恢复 + 参数脱敏**

`safeExecute` 包装 panic 恢复，单工具崩溃不影响进程；`AuditDecorator` 对敏感参数（手机号、身份证、token）做摘要脱敏，满足审计合规同时不泄露敏感信息。

### 4.2 差距与短板

**短板 1：Schema 手写**

每个工具的 `Parameters()` 方法都需手写 `map[string]ToolParam`，无法从 Go struct 自动反射生成。Python 生态借助 Pydantic V2 可实现"写函数即工具"，开发效率比 HiveMTK 高一个量级。这是 HiveMTK 工具开发最大的 DX 痛点。

**短板 2：无流式工具**

所有工具都是 `Execute(ctx, args) (ToolResult, error)` 同步返回。对于 RAG 检索（可能返回长文档）、批量触达（20 个渠道并发）、订单批量查询等长任务，无法流式输出，用户需等待完整结果。OpenAI Agents SDK、LangGraph、AutoGen、Google ADK、Eino 均支持流式。

**短板 3：无 MCP 协议**

无法消费外部 MCP server（如官方 GitHub MCP、Filesystem MCP），也无法被 Claude Desktop / Cursor / Windsurf 消费。在 MCP 生态快速扩张的当下，这等于自绝于工具生态。

**短板 4：ToolRouter 死代码**

`tool_router.go` 已实现完整的熔断 + 限流 + 成本统计 + 全局统计，但 `router.Setup` 中未装配。代码完整却未生效，是明显的工程债。

**短板 5：HTTP API 不完整**

只暴露权限管理 API（`/api/agent/tools/permission/*`），没有 `/tools/list`、`/tools/execute`、`/tools/stats` 调试入口。运维与集成方无法通过 HTTP 直接验证工具，只能走 LLM 链路，调试成本高。

**短板 6：审计/计费内存版**

`MemoryAuditLogger` 与 `MemoryCostTracker` 重启即丢失，无法跨实例聚合。多实例部署时无法看到全局调用画像。`db_audit_persister.go` 已有雏形但未启用。

**短板 7：无工具元数据**

`Tool` 接口没有 `Version() / Author() / Deprecated() / Tags()` 方法，无法做版本管理与废弃追踪。长期演进后会出现"哪些工具该下线"的治理盲区。

**短板 8：无热加载**

`Unregister` 存在但需小心调用，无正式的热加载机制。新增工具必须重启服务。

**短板 9：结果截断简单粗暴**

4000 字符硬截断 + "已截断"提示，无智能摘要。对于长 RAG 结果，截断后模型可能丢失关键信息。理想方案是基于 token 估算 + LLM 摘要。

**短板 10：NoOp 权限检查器默认放行**

生产环境装配的是 `NoOpPermissionChecker{}`，依赖上层 SalesEngine 把关。一旦 SalesEngine 出现 bypass 路径，工具链无二次防线。

**短板 11：BatchExecute 并发无 sem**

`BatchExecute(parallel=true)` 模式无并发上限，可能打爆下游。`DispatchByLLMToolCall` 有 `maxConcurrent=5`，但 `BatchExecute` 未复用此机制。

**短板 12：ToolContext 通过 context.Value 传递**

`context.Context` 中通过 `context.Value` 传递 `ToolContext`，类型不安全，编译期无法发现 key 冲突。理想方案是将 `ToolContext` 作为 `Execute` 的显式参数。

```go
// internal/aiagent/agent/tooluse/provider.go
type ToolProvider interface {
    Name() string                                    // 唯一名称
    Category() ToolCategory                          // 工具分类
    Description() string                             // 描述
    Provide(ctx ProviderContext) ([]Tool, error)     // 工厂方法
}

type ProviderContext struct {
    DB     *gorm.DB
    Config ProviderConfig  // 配置驱动启停
}

type ProviderRegistry struct {
    providers map[string]ToolProvider
    order     []string  // 注册顺序
}

func (r *ProviderRegistry) RegisterProvider(p ToolProvider) error
func (r *ProviderRegistry) RegisterAll(ctx ProviderContext, toolRegistry *ToolRegistry) ([]ProviderRegistrationResult, error)
```

**5 个内置 Provider 包装原有 registerAgent\*Tools 函数**：

| Provider                | Category   | 工具数 | 原 register 函数                  |
|-------------------------|------------|--------|-----------------------------------|
| ReachToolProvider       | reach      | 20     | registerAgentReachTools           |
| PrivateMessageToolProvider | pm     | 3      | registerAgentPrivateMessageTools  |
| CustomerToolProvider    | customer   | 8      | registerAgentCustomerTools        |
| KnowledgeToolProvider   | knowledge  | 4      | registerAgentKnowledgeTools       |
| BusinessToolProvider    | business   | 5      | registerAgentBusinessTools        |

**第三方扩展两种方式**：

```go
// 方式 1：在 router 包显式注册
providerRegistry.RegisterProvider(&MyProvider{})

// 方式 2：在第三方包 init() 中自注册（推荐）
func init() {
    tooluse.RegisterToolProvider(&MyProvider{})
}
// main 包通过空白导入触发：import _ "marketing/internal/mytools"
```

**配套 HTTP API**：`GET /api/agent/tools/providers` 返回所有 Provider 装配状态（含 tool_count / skipped / err / duration_ms）。

**配套 Build\*Tools 工厂函数**：抽取 `BuildReachTools / BuildCustomerTools / BuildKnowledgeTools / BuildBusinessTools / BuildPrivateMessageTools`，返回 `[]Tool` 不注册到 Registry，让 Provider 通过 Provide() 返回工具列表，由 ProviderRegistry 统一装配。

**配置驱动启停**：通过 `ProviderConfig.Enabled=false` 跳过整个 Provider；通过 `ProviderConfig.DisabledTools=[]string{"reach.sms.send"}` 精细禁用单个工具。

**收益**：
1. 新增工具集（如 analytics / iot / bi）无需修改 `registerAllAgentTools`，只需实现 ToolProvider 接口
2. 第三方包可通过 `init()` 自注册，零侵入
3. 配置驱动启停整个 Provider 或单个工具
4. `/api/agent/tools/providers` 让运维侧可视化所有扩展点
5. 不破坏向后兼容：原有 `registerAgent*Tools` 函数保留作为 Provider 内部实现

```go
    Deprecated   bool
    DeprecatedBy string  // 替代工具名
    Tags         []string
    Category     ToolCategory
}

type Tool interface {
    // ... 原有方法
    Metadata() ToolMetadata
}
```

`BaseTool` 提供默认实现，旧工具零改动；新工具通过 `BaseTool.WithMetadata()` 配置。

**P2-10：智能结果截断**

替代 4000 字符硬截断，引入两层策略：
1. **基于 token 估算**：使用 tiktoken Go 移植版估算结果 token 数，超阈值进入摘要流程；
2. **LLM 摘要**：对超长结果调用轻量 LLM（如 GPT-4o-mini / 通义千问-turbo）生成 200 字摘要，附原长度提示。

为避免摘要本身成为性能瓶颈，增加结果缓存（key = hash(原始结果)）。

### 5.4 P3 长期路线图（半年规划）

**P3-11：工具沙箱**

敏感工具（如自定义 HTTP 调用、动态 exec、用户上传脚本）通过子进程或 WASM 沙箱执行：
- **子进程方案**：`os/exec` + cgroup 资源限制（CPU / 内存 / FD）；
- **WASM 方案**：`wazero`（纯 Go WASM 运行时），用户上传 WASM 模块，沙箱内执行，无文件系统访问。

沙箱内工具崩溃不影响主进程，资源超限自动终止。

**P3-12：工具热加载**

基于 Go plugin 机制或容器化隔离实现热加载：
- **Go plugin**：`.so` 动态库加载，限制为 Linux 平台；
- **容器化**：每个工具独立容器，通过 gRPC 桥接，支持跨语言。

配合工具元数据中的 `Version` 字段，支持灰度发布与回滚。

**P3-13：跨语言工具**

通过 gRPC / HTTP 桥接 Python 生态工具，复用 LangChain / LlamaIndex 等成熟实现：
- 定义 `RemoteTool` 适配器，将远端 gRPC/HTTP 服务包装为本地 `Tool` 接口；
- 支持 LangChain `@tool` 装饰器导出为 gRPC 服务（借助 LangServe）。

## 六、实施风险与回滚预案

| 风险 | 影响 | 缓解 | 回滚预案 |
|------|------|------|---------|
| 装配 ToolRouter 改变执行路径 | 中 | 保留旧路径，通过配置开关 `executor.enable_router` 切换；灰度 10% 流量观察 24h | 关闭开关，回退到纯装饰器链路径 |
| HTTP 调试 API 暴露内部能力 | 高 | 必须走 auth 中间件 + 权限校验 + 限流；仅生产环境只读，开发环境可写 | 通过 feature flag 关闭 API |
| 流式接口侵入 Tool 抽象 | 中 | 设计为可选接口 `StreamReader`，旧工具零改动；`ToolExecutor` 自动检测 | 不实现 `StreamReader` 的工具走原同步路径 |
| 审计日志落 DB 影响主链路性能 | 中 | 异步批量写入（buffer 1000 + 1s flush）；DB 故障时降级到内存版 | 配置开关 `audit.backend=memory\|db` |
| Schema 反射生成与手写行为不一致 | 中 | 单元测试覆盖所有现有工具，对比反射生成与手写 schema 的 JSON 一致性 | 提供 `tooluse.UseLegacySchema()` 回退到手写 |
| MCP 适配引入新依赖 | 低 | 独立包 `mcpbridge`，不污染核心 `tooluse`；MCP SDK 依赖 Go module 隔离 | 关闭 MCP bridge，不影响本地工具链 |
| BatchExecute 并发上限改变默认行为 | 低 | 默认值 10 兼容现有场景；可通过配置上调 | 配置 `batch.max_concurrency=0` 表示无限制 |
| 工具元数据接口扩展破坏旧工具 | 低 | `BaseTool` 提供 `Metadata()` 默认实现返回空元数据 | 旧工具不实现 `Metadata()`，自动走默认 |

**通用回滚原则**：所有 P0/P1 优化必须通过 feature flag 控制，确保可在不重新部署的情况下回退；P2/P3 优化独立成包，不影响核心链路。

## 七、结论

HiveMTK 工具链机制在 `internal/aiagent/agent/tooluse/` 单包内沉淀了 41 个业务工具、8 层装饰器链、单例注册中心、LLM Function Calling 调度器、白名单权限模型与内存可观测性闭环，并通过 `portcontract` 独立包打破 import cycle，在**企业级容错能力与五层架构合规性**两个维度上显著领先本调研覆盖的所有开源方案（OpenAI Agents SDK、LangChain/LangGraph、CrewAI、AutoGen、Google ADK、MCP、langchaingo、Eino）。

然而，HiveMTK 在**开发者体验（Schema 手写）、生态开放性（无 MCP）、异步与流式能力、可观测性闭环（审计内存版、HTTP API 不完整）**四个维度上存在明显短板。其中 Schema 手写是工具开发效率的核心瓶颈，无 MCP 协议是工具生态开放性的核心缺口，这两项是 HiveMTK 工具链下一阶段必须优先补齐的能力。

基于本调研，建议按以下优先级推进优化：
- **本迭代（P0）**：装配 ToolRouter、新增 HTTP 调试 API、编写综合测试；
- **下迭代（P1）**：流式工具接口、审计落 DB、Schema 反射生成、BatchExecute 并发上限；
- **季度内（P2）**：MCP 协议双向适配、工具元数据、智能结果截断；
- **半年内（P3）**：工具沙箱、热加载、跨语言工具桥接。

P0 三项是低成本高收益的"清债"工作，预计 2-3 人日即可完成；P1 四项是工程效率与可观测性的关键补强，预计 1-2 迭代落地；P2 三项决定 HiveMTK 能否融入 MCP 工具生态，建议作为季度 OKR；P3 三项是长期演进方向，可根据业务需求择机推进。

**核心判断**：HiveMTK 工具链机制已具备企业级生产可用的工程底座，当前阶段的优化重心应从"补齐容错能力"转向"提升开发效率与生态开放性"。装饰器链已是行业最强，下一步要让工具"好写、好用、好对外"。
